## 检索预算与切片粒度如何划定 RAG 与长上下文的可比边界

### 一、本节结论状态：不足以划定边界

本节三个候选命题（检索质量阈值边界、chunk_size×top-k 交互、成本优势的适用范围）在现有材料下均被判定为 **insufficient_evidence**，审查记录的原因码为 `material_excerpt_truncated`，即已获取的全文材料在实验设置、方法与结果块上存在截断，无法完成条件齐备性核验。因此本节只能报告「本批材料中若干作品在各自设置下报告了什么」，不能给出「在固定任务、模型与语料版本下，检索预算与切片粒度如何划定可比边界」的定量结论。

需要特别说明：本节所有可用证据中，**没有任何一条同时报告了 task、dataset、model、corpus_version、retriever、chunk_size、top_k、context_budget、metric 这九项必要条件**。这意味着即便某些论断方向一致，也无法确认它们处于同一实验设置，不能合并为「同一设置下的验证」。

### 二、本批材料中作品报告了什么

**（1）关于 RAG 与长上下文的总体性能关系**

有作品在固定模型（Gemini-1.5-Pro、GPT-4O、GPT-3.5-Turbo）与语料下报告：RAG 的性能低于长上下文方法 [E:fact_8633117a99ce11a845eea1ed]。该表述为原文引用绑定，但其对应的任务、数据集、切片粒度、top-k 与上下文预算取值未在可用材料中完整给出，因此只能作为「某作品在其设置下的报告」，不能推广为一般性结论。

需说明：本小节（1）（2）（3）（7）所引证据均来自同一来源（arxiv:2407.16833v1），属同一来源的多条证据，按 unknown_independence 规则不应计为多个独立支持，以下并列呈现仅为汇总该来源的报告内容。

**（2）关于 top-k 增大后的收敛现象**

同一作品方向的多条材料指出：随着检索 top-k 增大，RAG 性能提升并逐渐接近长上下文性能，当 top-k > 50 时两者性能相似 [E:fact_c7b5d795bdfc598e6ae42131]；top-k 较小时 RAG 性能较低，top-k 较大时两者相似 [E:fact_100f31b01a8eea16bfb4875a]；增加 top-k 可提升 RAG 性能使其接近长上下文 [E:fact_2427333a6685609b267a4d02]。

这三条材料指向同一现象，但它们的 `provenance_status` 均为 `source_only`，即**未提供可核验的原文引用片段**，属于来源级记录而非原文验证。此外，它们未报告 chunk_size、context_budget 与评测指标的具体取值，无法判断「top-k > 50 时性能相似」这一阈值是否在输入预算对齐的前提下成立——若长上下文一侧的输入预算远大于 RAG 一侧，则「相似」本身可能只是预算不对等的产物。因此该现象只能作为线索，不能作为边界结论。

**（3）关于检索质量足够高时的成本优势**

有材料报告：在输入 token 预算受限且检索质量足够高（Self-Route 达到与长上下文可比性能）时，RAG 具有显著的单位质量成本优势，节省 38%–61% 的 token 使用量 [E:fact_3f53bb21d5975ffa41eef046]。该条同样为 `source_only`，且「检索质量足够高」未给出 recall/precision 的量化阈值，无法据此确定边界位置。

另有材料报告混合方法 Self-Route 在性能上显著优于纯 RAG，且接近或超过长上下文方法（GPT-4O 下降 0.2%、Gemini-1.5-Pro 下降 2.2%、GPT-3.5-Turbo 提升 1.7%）[E:fact_dea7765e958f96cf8693cb60]。该条为引用绑定，说明在特定路由策略下 RAG 的劣势可被弥补，但路由策略本身改变了方法类别，不能直接用于划定「纯 RAG vs 长上下文」的边界。

**（4）关于检索结果被截断时的性能下降**

有材料在长文档问答任务中报告：当检索结果被截断（Trunk Size）或摘要化导致信息丢失时，使用完整长上下文的方法表现优于 RAG [E:fact_64c2d0abcf35c3eb858990e2]。该条为引用绑定，其原文片段直接支持「截断导致性能下降」这一方向性结论；证据内容字段中另载有具体数值（GPT-4o 截断 512 token 得 0.549、完整长上下文 0.579；Qwen2-72B 截断 512 token 得 0.353、完整长上下文 0.468），但该数值未出现在原文片段中，属待核验内容。但它报告的是「截断导致信息丢失」这一特定条件下的对比，其 chunk_size 与 top-k 取值、以及长上下文一侧的输入预算是否与 RAG 一侧对齐，在可用材料中未完整呈现，因此不能直接外推为「检索预算边界」的一般规律。

**（5）关于临床 NLP 分类任务中的等效性**

有材料报告：在临床 NLP 分类任务中，RAG 的性能与长上下文方法相当，统计检验显示差异不显著 [E:fact_daf52db143cbf44e9f85d642]；该等效性在 GPT4o、LLaMA 和 Mistral 三种模型上均成立，DeLong 检验确认 AUROC 差异统计不显著 [E:fact_79f7232014c89d5552d00d68]。

需要注意任务类型差异：这是**分类任务**而非长文档问答，其评测指标为 AUROC 而非 answer accuracy 或 faithfulness。按条件可比性要求，该材料属于「别的设置下的作者报告」，**不得计入本节长文档问答命题的支持或反驳**。它只能提示：任务类型（分类 vs 问答）本身可能是边界位置的重要调节变量。

**（6）关于成本与延迟**

以下成本与延迟数值均来自临床分类场景，不得外推到长文档问答场景。有材料报告：在相同任务与模型下，RAG 相比长上下文节省超过 90% 的成本（token 数量从 1.72 亿降至 1320 万）[E:fact_ccd41eacb6d73046d62fc607]；具体为 GPT-4o 全长上下文约 1.72 亿 tokens、费用 430 美元，分块 RAG 仅需 1320 万 tokens、费用约 33 美元 [E:fact_531a6f866cb6722f9e345bcf]；RAG 还通过减少输入长度提高推理速度，Mistral 每患者从 1.11 秒降至 0.90 秒（19%），LLaMA 从 0.58 秒降至 0.45 秒（23%）[E:fact_3554d230f6ed2ef6a254f43b]。

这些数值来自临床分类场景，且价格与延迟均绑定特定时间点的 API 定价与硬件条件。按本节成本命题的必要条件（input_tokens、output_tokens、latency_definition、hardware_or_price_date、metric），可用材料未完整报告这些字段，因此无法判断该成本优势在定价或延迟定义改变后是否仍然成立。

**（7）关于 RAG 的失败模式**

有材料指出 RAG 失败的主要原因包括需要多步推理和隐含的全局理解需求 [E:a29dafbf6051e6cdc8e64035]。该条为 `source_only`，未给出量化结果，但提示了边界的一个可能维度：任务所需的推理步数与全局理解程度，可能比单纯的检索预算更能决定 RAG 与长上下文的分野。

### 三、为什么无法划定边界：三个卡点

**卡点一：必要条件系统性缺失。** 本节命题要求九项条件齐备，但可用证据中无一条同时报告全部九项。最常缺失的是 chunk_size、context_budget 与 metric 的具体取值。缺少 context_budget 尤其致命——「输入预算对齐」是本节全部比较的前提，若无法确认两侧预算是否对齐，任何性能差都无法归因于检索方法本身。

**卡点二：多数材料为 source_only。** 本批可用证据中，仅 10 条为 `quote_bound`（有可核验原文片段），其余 10 条为 `source_only`。source_only 不是原文验证，不能作为定量结论的支撑。

**卡点三：任务与指标不可比。** 现有材料横跨长文档问答、临床分类、通用问答等多种任务，指标涵盖 answer accuracy、AUROC、token 成本、延迟等。按条件可比性规则，这些材料只能各自作为「别的设置下的作者报告」，不能合并计入同一命题的支持或反驳计数。

### 四、可操作的下一步核验方向

若要将本节从 insufficient_evidence 推进到可判定状态，需要优先补齐以下材料：

1. **同一作品内同时报告 chunk_size、top-k、context_budget 与 metric 的对照实验**，且长上下文一侧的输入预算与 RAG 一侧明确对齐；
2. **检索 recall/precision 的量化值与最终性能的联合报告**，用于确定「检索质量阈值」是否存在及其位置；
3. **同一任务下 answer accuracy、faithfulness、evidence recall 三种指标的同向或反向报告**，用于检验边界结论是否指标依赖；
4. **成本与延迟的完整字段**（input_tokens、output_tokens、latency_definition、hardware_or_price_date），用于判断成本优势的适用范围。

在补齐上述材料之前，本节只能给出方向性提示：top-k 增大可能使 RAG 向长上下文收敛 [E:fact_c7b5d795bdfc598e6ae42131]（该条为 source_only，未验证），检索结果被截断导致信息丢失时长上下文占优 [E:fact_64c2d0abcf35c3eb858990e2]，以及任务所需的全局理解程度可能是比检索预算更根本的边界变量 [E:a29dafbf6051e6cdc8e64035]（该条为 source_only，未验证）。这些均为线索，不构成已证实的边界结论。

## 性能与成本结论的适用模型、资源与工作负载范围

### 一、本节可核验的证据边界

本节要求所有成本结论绑定价格日期或硬件条件，且比较需在同一设置下进行。经审查，当前交付材料中**没有任何一条证据同时满足**「task、model、input_tokens、output_tokens、latency_definition、hardware_or_price_date、metric」七项必要条件，因此本节无法给出 RAG 与长上下文之间可比较的单位质量成本结论。以下仅能报告各材料在**各自设置下**的硬件、模型与工作负载事实，并明确标注其不可外推的边界。

### 二、硬件与模型条件（各自设置，不可直接比较）

- Sarathi-Serve 的评估硬件为 NVIDIA A100 (80GB) 与 A40 (48GB) GPU，运行于 Azure VM；评估模型包括 Mistral-7B、Yi-34B、LLaMA2-70B、Falcon-180B [E:fact_ee83541b80c94b7e7483170a][E:fact_f95ed3060a4418eabad7f663]。该材料**未报告价格日期**，因此其吞吐-延迟结论无法换算为货币成本，也无法与任何按 token 计价的 API 成本结论对齐。
- REFRAG 实验的解码器包括 LLaMA-2 (7B/13B)、LLaMA-3.1 (8B)、LLaMA-3.2 (3B)，编码器为 RoBERTa-Base/Large [E:fact_b0c1c1731b00bdc0203529cf]。该材料同样**未报告硬件型号与价格日期**，其「压缩上下文性能与 Full Context 相当」的结论 [E:fact_98ae175a37d095b091d2f8e2] 是质量侧结论，**不构成成本侧证据**。

### 三、延迟定义与工作负载条件

- 延迟在本批材料中被定义为两个指标：TTFT 的中位数，以及 TBT 的 P99 [E:fact_8a2dde2f9e5f98d39437c1e7]。SLO 阈值以「无干扰解码迭代时间的 5 倍（严格）与 25 倍（宽松）」定义，而非绝对毫秒值 [E:fact_9aa8f80b0c25b7e560cae47d]。这意味着该延迟定义**绑定于特定模型-硬件对**，跨硬件外推会改变阈值含义。
- 在严格 SLO 下使用 512 token 预算、宽松 SLO 下使用 2048 token 预算 [E:fact_a6ffd5041b9fa26948c8ba92][E:fact_fc63946bb57b6b514a5ee71b]，说明「延迟定义」本身会改变系统的 token 预算配置，进而改变输入 token 规模——成本与延迟在此设置下不可分离。
- 工作负载长度分布对系统容量有直接影响：arxiv_summarization（中位数 7059 tokens）的吞吐容量低于 openchat_sharegpt4（中位数 1730 tokens）[E:fact_6df3c298e7e4280fc7f85aa1]。这是**长提示词工作负载下容量下降**的直接证据，但该结论绑定于上述 A100/A40 硬件与四个特定模型，**未报告价格日期**，不能外推为「长上下文方法在任何硬件上都更贵」。

### 四、检索侧配置对成本-质量权衡的间接影响

- 在 RAG 系统中，chunk size 显著影响检索质量：短事实型数据集最佳为 64-128 tokens，描述性或技术性响应需要 512-1024 tokens [E:fact_db634627807aaa28a7dd365b]；SQuAD 上 64-token chunk 的 recall@1 最高（64.1%），增大到 512 tokens 反而下降 10-15% [E:fact_3b84b915a8f91b86ea932f00]；NarrativeQA（51830.4 tokens/document）上 64-token chunk 的 recall@1 仅 4.2%，1024 tokens 提升至 10.7% [E:fact_a4596359ed9e4ab51774aa8b]。上述三条证据均来自同一来源（arxiv:2505.21700v2），不构成独立验证。
- 这些结果说明：**chunk size 与任务类型共同影响检索质量**，而检索质量随 chunk size 非单调变化。因此「RAG 更省 token」这一说法必须绑定 chunk size、top-k 与任务类型才有意义；本批证据片段**未包含 top-k 取值，也未报告任何货币价格**，故无法计算单位质量成本。
- 压缩侧另有旁证显示：剪枝方法在压缩率 50% 时困惑度急剧上升、负面评价得分下降，但作者指出这并非「生成无害内容」，而是模型已无法生成有效语言 [E:fact_eb94e00773327556adc81c9c]；该评估以困惑度为主指标、在 WikiText-2 上进行 [E:fact_85b3adb0746ef0765c550160]。该证据的 source_quote 为空、provenance_status 为 source_only，无法核验其是否真正支持上述论断。这提示**压缩带来的 token 节省可能以质量崩塌为代价**，但该证据属于语言建模评估，**不是长文档问答的成本-质量证据**，仅作旁证，不能外推到长文档问答场景。

### 五、结论状态

本节三个假设（h1 检索质量边界、h2 chunk/top-k 交互、h3 成本-质量适用范围）的评估状态均为 **insufficient_evidence**，原因代码为 `material_excerpt_truncated`，且 `materials_reviewed` 为 0。具体而言：

- **h3（成本-质量适用范围）**：必要条件中 `hardware_or_price_date`、`input_tokens`、`output_tokens`、`latency_definition` 在交付材料中均无同时齐备的记录。Sarathi-Serve 提供了硬件与延迟定义，但**未报告价格日期与输入/输出 token 成本**；REFRAG 提供了模型配置，但**未报告硬件与价格**。两者设置不可比，不能合并为同一设置下的成本比较。
- **跨条件外推的边界**：现有材料只能支持「在 A100/A40 硬件、特定四个模型、特定 SLO 定义下，长提示词工作负载的吞吐容量更低」这一**窄结论** [E:fact_6df3c298e7e4280fc7f85aa1]，且该结论**不含价格维度**。任何「RAG 比长上下文便宜 X%」或「长上下文价格下降后优势反转」的表述，在本批材料中**均无证据支持**。
- **工作负载反转**：材料显示较长提示词工作负载的吞吐容量低于较短提示词工作负载 [E:fact_6df3c298e7e4280fc7f85aa1]，且 chunk size 的最优值在 SQuAD 与 NarrativeQA 两个数据集间呈现差异 [E:fact_db634627807aaa28a7dd365b][E:fact_3b84b915a8f91b86ea932f00][E:fact_a4596359ed9e4ab51774aa8b]，但**没有任何材料在同一设置下同时测量 RAG 与长上下文的成本与质量**，因此「成本优势是否反转」无法判定。

**建议的后续核验条件**：需要找到在同一 task、同一 model、同一价格日期下，同时报告 RAG 与长上下文方法的 input_tokens、output_tokens、延迟定义与质量指标的研究；或找到明确标注 API 价格日期与硬件型号的成本对比实验。具体可优先核验以下方向：（1）在 LongBench、∞Bench 或 NarrativeQA 等长文档问答基准上，对同一模型分别采用 RAG（固定 chunk size 与 top-k）与长上下文直接输入，并同时报告质量指标与 token 成本；（2）检索侧需补充 retriever 类型（BM25/稠密检索）、corpus_version 与 top-k 取值，以补全 retrieval_boundary 的 required_conditions；（3）工作负载维度需补充查询频率与并发设置，以检验成本优势是否随负载反转。在此之前，本节所有成本结论应标记为 insufficient_evidence。
